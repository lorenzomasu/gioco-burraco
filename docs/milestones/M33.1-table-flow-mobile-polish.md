# Milestone 33.1 — Table Flow & Mobile Polish

## Goal

Correct the most important usability issues found during hands-on playtesting of the released v1.1 table before starting v1.2 feature work. Make turn order immediately understandable, keep the public meld state visible at a glance without ordinary internal scrolling, slow normal bot choreography enough to follow the game, and reduce the remaining dashboard-like feel of the active table. Ship the reviewed result as patch release `v1.1.1` without changing Burraco rules or domain semantics.

## Context

The released `v1.1.0` SHA is `2cbf5327abe0c435009d0431756eba90eb853324`. The post-v1.1 workflow/roadmap alignment is on current `main`.

Current implementation details that motivate this milestone:

- `GameTable.tableSeats` deliberately places the teammate on the left and opponents at top/right. With the human at the bottom and player order `player-1 → player-2 → player-3 → player-4`, this obscures the natural clockwise reading of turns.
- `.meld-list` currently has a fixed max-height with `overflow: auto`, and `.meld__cards` can scroll horizontally. This makes already-public table state require local scrolling.
- normal bot playback currently uses a fixed 550 ms delay between committed steps, while visible motion may consume most of that interval.
- M27–M32 improved layout, direct manipulation, motion, sound and app-wide UX, but the active table still has nested panel/chrome weight that makes mobile play feel more like operating controls than playing directly on a table.

Preserve the engine/React boundary, deterministic bot legality, hidden-information guarantees, persistence model, motion/audio safety and all keyboard/touch alternatives already established by v1.1.

## In scope

- Remap visual seating so the human is bottom, teammate is top/opposite, and the two opponents are left/right in clockwise turn order.
- Strengthen the active-turn visual cue so the current player can be located immediately without reading the history panel.
- Replace ordinary meld-area internal scrolling with adaptive-density presentation that keeps every public meld simultaneously visible in the live table.
- Adapt card size, overlap, grid density, labels and spacing as meld count/card count grows, while preserving readable rank/suit identity and Burraco/wildcard meaning.
- Rework normal bot playback timing so individual public actions and player-to-player transitions are followable. Keep fast playback and `Completa subito`.
- Refine the active-table presentation to reduce unnecessary nested chrome, spacing and persistent instructional weight, especially on 320–390 px mobile widths, while keeping controls discoverable and accessible.
- Update focused component/browser tests and architecture documentation for the corrected seat mapping, meld presentation and playback timing.
- Bump package metadata/product-facing release version to `1.1.1` and update release documentation required for the patch release.

## Out of scope

- Any change to player IDs, team membership, actual engine turn order, starting-player rotation or Burraco rules.
- Bot decision quality, candidate generation, difficulty levels or hidden-information behaviour.
- Match-length configuration or persistence-schema redesign planned for M34.
- New onboarding/tutorial system planned for M36.
- PWA/service-worker/offline infrastructure planned for M37.
- New card art/theme system, background music, replay/history system or online multiplayer.
- Replacing the existing direct-manipulation model or removing keyboard/button fallbacks.
- Large animation/UI framework dependencies.

## Required behaviour

### 1. Seating and clockwise turn flow

The visual table must map the existing four-player turn order around the human as follows:

- bottom: human `player-1`;
- left: the player immediately after the human in the current clockwise order (`player-2` in the standard setup);
- top/opposite: the human teammate (`player-3` in the standard setup);
- right: the remaining opponent (`player-4` in the standard setup).

Derive the mapping from player order/team identity rather than hardcoding labels that would become false if names change. This is presentation-only: no state under `src/game` may change merely to produce the seating.

The active seat/turn indication must be visually stronger than inactive seats and understandable without opening bot history. Text/status announcements remain authoritative for assistive technology.

### 2. Melds are board state, not scroll content

Both teams' public meld areas must show all melds simultaneously in the live table. Ordinary play must not require vertical scrolling inside `.meld-list` or horizontal scrolling inside individual `.meld__cards` to discover a meld or identify its cards.

Use adaptive density rather than clipping/removing information. The implementation may change:

- number of grid columns;
- card width/height;
- negative overlap between cards;
- inter-meld gaps/padding;
- metadata prominence;
- label/badge placement;
- responsive breakpoints or container-query rules.

As density increases, preserve at minimum:

- each meld remains a distinct target/group;
- the visible corner of every card exposes rank and suit (or Joker identity);
- wildcard/pinella representation remains available and understandable;
- Burraco classification remains textually available;
- the human team's melds remain valid direct-manipulation destinations;
- no card/meld is omitted merely to make the layout fit.

At 320, 390, 768 and representative desktop widths, the table must choose an appropriate density automatically without document-level horizontal overflow. The implementation must include stress fixtures/states with many simultaneous melds and long sequences, not only an early-round empty table.

If one legal extreme cannot satisfy both full simultaneous visibility and the existing minimum-readable typography at 320 px, do not silently restore local scrolling. Implement a deliberate compact overview treatment that still exposes every meld/card identity, and record the exact residual readability trade-off in the implementation report.

### 3. Followable bot choreography

Normal playback must be materially slower than the released 550 ms fixed cadence and must allow the player to perceive action → result → next action.

Use presentation-only timing; do not delay or change engine commits, bot legality or saved state. The normal cadence must satisfy these concrete targets:

- at least 900 ms before the next ordinary committed bot step;
- at least 1200 ms after a public meld play, meld extension, discard/player hand-off, newly reached Burraco, or pozzetto acquisition before the next bot step;
- motion must finish within the available normal cadence rather than being immediately visually overwritten;
- the first automated action after control leaves the human must not occur in less than 900 ms.

`fast` remains intentionally fast and may keep the existing short cadence unless implementation evidence requires a small compatibility adjustment. `Completa subito` still resolves the pending bot chain immediately and suppresses/cancels stale intermediate presentation as before. Changing playback speed while a timer is pending must continue to cancel/reschedule safely.

Timing classification may use existing committed feedback/public-event metadata; it must not inspect hidden bot information or duplicate game rules.

### 4. Active-table polish

Refine the active-match screen so the table, cards and current turn dominate over UI framing.

The implementation should remove or soften unnecessary nested panel borders/backgrounds, reduce wasted vertical space, and make persistent explanatory copy secondary to the actual playable state. Do not achieve “polish” by hiding required information behind obscure controls.

On 320–390 px mobile:

- the current turn, central piles, public melds, human hand and primary action path must read as one coherent game surface;
- primary controls remain reachable with at least the existing touch-target/accessibility guarantees;
- settings/help/history/new-match controls remain available but visually secondary;
- no new body-level horizontal scrolling is introduced;
- the user must not need to open a disclosure merely to know whose turn it is or what public melds exist.

Preserve existing focus management, live regions, dialog behaviour, reduced-motion handling, audio preferences, drag/touch fallbacks and error feedback.

### 5. Release patch

Update `package.json`, root `package-lock.json`, README current release metadata and `docs/RELEASE.md` as needed for `v1.1.1`.

The implementation agent stops after implementation/report/commit/push. Independent review, PR/CI/merge, post-merge production verification and creation of tag `v1.1.1` remain the merge/release gate defined by `docs/WORKFLOW.md` and `docs/RELEASE.md`.

## Acceptance criteria

- [ ] AC1 — With the human at bottom, their teammate renders opposite at top and opponents occupy left/right in the existing clockwise player order; no domain player/team/turn-order state changes.
- [ ] AC2 — Current-player emphasis makes each turn visually locatable on the appropriate seat/table area without opening bot history, while existing accessible turn announcements remain correct.
- [ ] AC3 — Meld areas no longer use ordinary vertical internal scrolling and individual meld card rows no longer use ordinary horizontal scrolling as the mechanism for discovering public state.
- [ ] AC4 — Stress states with multiple melds and long sequences render every public meld and every card identity simultaneously through adaptive density at 320, 390, 768 and desktop widths, with no document-level horizontal overflow.
- [ ] AC5 — Own-team direct-manipulation targets, click/keyboard extension controls, wildcard annotations and Burraco labels remain operable/readable after density changes.
- [ ] AC6 — Normal bot playback enforces ≥900 ms ordinary cadence and ≥1200 ms after significant public actions/hand-offs defined above; the first bot action after the human turn also waits ≥900 ms.
- [ ] AC7 — Fast playback and `Completa subito` retain their existing semantics; speed changes, unmount/new match and immediate completion leave no stale timer/motion callbacks.
- [ ] AC8 — At 320–390 px the active match has materially reduced dashboard chrome/vertical waste while keeping central piles, meld state, hand and primary actions understandable and reachable; Settings/Help/history/new-match remain available but secondary.
- [ ] AC9 — Existing save/resume, audio, reduced-motion, focus, keyboard, touch/drag, hidden-information and engine-legality behaviour is unchanged.
- [ ] AC10 — No game-rule, bot-strategy, scoring, persistence-schema, M34+ feature or new heavy runtime dependency is introduced.
- [ ] AC11 — Product metadata is `1.1.1`, release docs describe the patch exact-SHA gate, and the implementation report records tested viewport/stress fixtures plus any residual density trade-off.

## Required tests

Add/update automated regression coverage for:

- seat mapping: human bottom, teammate top, next clockwise opponent left, remaining opponent right;
- active-seat indication across at least human → bot → teammate/opponent transitions;
- dense meld fixtures with several simultaneous melds and at least one long sequence, asserting that all meld/card nodes are present and no meld-list/meld-card local scroll is required at representative widths;
- 320 and 390 px browser checks for no document-level horizontal overflow and accessibility of primary controls;
- own-team meld drag/drop and keyboard extension after adaptive-density changes;
- deterministic normal playback timing using fake/browser clock: first bot action ≥900 ms, ordinary step ≥900 ms, significant event/hand-off ≥1200 ms;
- fast and immediate-completion regression paths;
- interruption cleanup for pending timers/motion;
- version/release metadata.

Do not replace behavioural assertions with screenshot-only snapshots. Browser geometry/CSS assertions are appropriate where the requirement is inherently layout-dependent. Include rendered/manual inspection notes for 320, 390, 768 and desktop in the implementation report.

# Milestone 33.2 — Flexible Wildcard Repositioning

## Goal

Change one rule-critical behaviour before v1.2: when extending an existing sequence, allow an already-active matta (jolly or pinella currently acting as wildcard) to change the rank it represents whenever the complete resulting set of physical cards forms a valid sequence. This deliberately replaces the stricter M15 history lock with the more permissive product variant requested after playtesting, while keeping the wildcard inside the same meld and preserving all other sequence legality rules.

Ship the reviewed correction as patch release `v1.1.2`.

## Context

The released `v1.1.1` baseline is `76a85445a31afe1bee9af217ea1b7006ccf4be24`.

Today `src/game/melds/validateMeldExtension.ts` first revalidates the full resulting meld, then applies an additional history-aware constraint: if an existing sequence wildcard would change `representedRank`, the extension is rejected with `WILDCARD_POSITION_LOCKED` unless the exact natural card for the previously represented rank was added. `docs/RULES.md` M15 documents that behaviour.

That extra history lock is now intentionally removed for same-sequence extensions. The pure final-state sequence validator remains authoritative: if the existing physical cards plus the newly added physical cards normalize to a valid sequence of the same suit/type, the extension is legal even when the stored wildcard changes represented rank or a same-suit pinella changes between natural/wildcard roles as part of the deterministic normalization.

Canonical playtest regression:

- existing table sequence: `Jolly=4♦, 5♦, 6♦, 7♦, 8♦`;
- player adds `10♦`;
- resulting legal sequence: `5♦, 6♦, 7♦, 8♦, Jolly=9♦, 10♦`.

The physical jolly is the same card before and after. Nothing returns to hand or transfers to another meld.

## In scope

- Remove the existing represented-rank history lock from same-sequence extension validation.
- Keep final-state validation through the existing deterministic meld/sequence validator.
- Preserve the existing requirement that an extension keeps the stored meld type and, for a sequence, the same suit.
- Allow the existing active wildcard to be deterministically reinterpreted to another represented rank when the final sequence is valid.
- Allow a same-suit pinella already present in the sequence to switch between natural-2 and active-wildcard roles when the final deterministic validation requires it.
- Preserve physical card IDs for every pre-existing and newly added card.
- Update engine/bot tests whose expected legality depended on `WILDCARD_POSITION_LOCKED`.
- Add a regression test reproducing the exact playtest case above through `extendMeld`, not only the pure validator.
- Add UI-level regression coverage proving the human can select/drop or use the accessible extension action for this case without receiving “Mossa non valida”.
- Update rule/architecture/release documentation and product version to `1.1.2`.

## Out of scope

- Moving a wildcard from one meld to another.
- Taking a wildcard back into the hand.
- Reordering/reinterpreting a meld without adding at least one card from the current player's hand.
- Allowing an otherwise invalid final sequence.
- More than the existing allowed number of active wildcards.
- Changing group/combinations semantics.
- Changing new-meld validation.
- Changing wildcard/pinella point values, Burraco classification rules, scoring or closure rules.
- Changing bot strategy priorities beyond the natural consequence that a newly legal extension may become a candidate through the shared legality engine.
- Any M34+ feature.

## Required behaviour

### 1. Resulting sequence validity is authoritative

For an existing sequence, `validateMeldExtension(existingMeld, addedCards)` must:

1. reject an empty extension as today;
2. revalidate all existing physical cards plus the newly added physical cards through the existing deterministic meld validator;
3. require the result to remain a sequence of the same suit;
4. accept the extension whenever that resulting sequence is valid, regardless of whether the pre-existing active wildcard keeps or changes its previous `representedRank`.

No separate “the wildcard must stay where it was” check may reject an otherwise valid resulting sequence.

### 2. Exact playtest case

Given an existing diamonds sequence whose stored semantic placements are equivalent to:

`Jolly=4♦, 5♦, 6♦, 7♦, 8♦`

adding the physical `10♦` from the current player's hand must succeed. The resulting sequence must normalize deterministically with the same physical jolly representing `9♦`.

The `10♦` is removed from the hand, the same team meld is replaced with the revalidated result, the player's turn remains in `action` unless an existing pozzetto/closure rule independently changes it, and no error is emitted.

### 3. Existing wildcard may move without exact replacement

Adding the previously represented natural card is no longer a prerequisite for changing a wildcard's represented rank.

Cases previously rejected solely with `WILDCARD_POSITION_LOCKED` must become legal when the full resulting sequence is valid. This includes an existing active jolly and an active pinella.

The previous “exact replacement” scenarios remain legal, but simply because their final sequence is valid, not because they unlock special history-aware permission.

### 4. Final invalidity still rejects

Flexibility is not an override of sequence rules. The extension must still be rejected if final validation fails for reasons such as:

- non-consecutive ranks after accounting for the one active wildcard;
- wrong suit;
- duplicate natural position;
- invalid Ace usage;
- too many active wildcards;
- sequence-size limit;
- physical duplicate-card ID;
- type change away from the stored sequence.

The existing engine error boundary may continue to surface these as `INVALID_MELD`; do not introduce UI-specific legality.

### 5. Physical identity and same-meld boundary

Every physical card already in the meld remains in that same meld after a successful extension. The matta that is reinterpreted is never removed, swapped for an abstract wildcard, returned to hand or moved to another team's/meld's collection.

The extension command still adds only the explicitly selected hand-card IDs.

### 6. Bots share the new legality automatically

Bot candidate generation and execution must continue to use the same extension validator/engine as the human. A bot may therefore consider a newly legal repositioning extension, but no separate bot-only wildcard rule or new strategy heuristic should be added.

Determinism and hidden-information boundaries remain unchanged.

### 7. Product rule documentation

Update `docs/RULES.md` to state explicitly that this game intentionally uses the flexible same-sequence wildcard-repositioning variant and supersedes the stricter M15 position-lock wording.

Do not continue to present the old FIBUR-style lock as implemented behaviour. Keep the broader FIBUR baseline attribution, but clearly mark this behaviour as a documented product variation.

Update `docs/ARCHITECTURE.md` so it no longer describes stored-sequence extension validation as preserving the prior represented position of an active wildcard. The final deterministic validated sequence is authoritative.

### 8. Patch release

Update root package metadata, README current release metadata and `docs/RELEASE.md` for `v1.1.2`.

The implementation agent stops after implementation, tests, report, commit and push. Independent review, PR/CI merge, production verification and tag creation follow `docs/WORKFLOW.md` and `docs/RELEASE.md`.

- [ ] AC8 — Bot candidate/execution paths use the same changed legality and remain deterministic/hidden-information safe, with no duplicate wildcard rule.
- [ ] AC9 — Group validation, new-meld validation, Burraco classification, scoring, closure, match lifecycle and persistence schema remain unchanged except for states reachable because the extension is now legal.
- [ ] AC10 — `docs/RULES.md` and `docs/ARCHITECTURE.md` accurately describe the flexible product variant and no longer claim that an active sequence wildcard's represented rank is locked.

## Required tests

- pure validator: an active same-suit pinella can be reinterpreted when the resulting sequence is valid;
- previously legal exact-natural replacement remains valid;
- a case where moving the wildcard cannot make the final cards consecutive remains invalid;
- wrong-suit and type-change regressions remain invalid;
- engine `extendMeld`: exact user playtest state succeeds, removes only `10♦` from the hand and updates only the target meld;
- engine immutability on an invalid extension;
- relevant bot candidate/strategy regression demonstrating shared legality without introducing bot-only rules;
- human UI/component or E2E regression for extending the exact table sequence with `10♦`, using the existing normal interaction path and asserting no rule-error alert;
- release metadata consistency for `1.1.2`.

Tests that currently assert `WILDCARD_POSITION_LOCKED` for an otherwise valid final sequence must be rewritten to the new accepted product rule, not deleted without replacement.

For rule-critical behaviour, include mutation-sensitive assertions: restoring the old history-lock branch should make the new regression tests fail.

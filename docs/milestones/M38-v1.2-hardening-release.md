# Milestone 38 — V1.2 Hardening & Release

## Goal

Turn the integrated M34–M37 v1.2 work into one verified release candidate and publish `v1.2.0` from one exact reviewed SHA.

M38 is a hardening and release milestone only. It must audit and close the remaining browser-level release gaps for configurable match length, bot difficulty, guided-first-match behaviour, save compatibility, installability/offline resume, and service-worker update/failure behaviour without adding new product features.

## Context

M38 starts from current `main` at:

`9a0b39ba2ff98b628af1a637758eb6572ec85585`

That baseline already contains M34–M37 and has a green main CI workflow.

Current v1.2 behaviour includes:

- M34: exactly 2, 3, or 4 smazzate, with 4 as default, plus save migration/compatibility;
- M35: exactly `easy` / **Facile** and `normal` / **Normale**, with Normale as default and the pre-M35 strategy baseline;
- M36: browser-local contextual guidance, enabled for the first guided match, dismissible and re-enableable from Settings, outside the active-match save;
- M37: installable production PWA, bounded app-shell precache, offline reload/resume after warm-up, production-only worker registration, no runtime caching, no forced `skipWaiting`/claim, and unchanged schema-v3 active-match persistence.

The existing browser suite already covers most of the release matrix:

- `e2e/lifecycle.spec.ts`: four-smazzata completion and two-smazzata completion;
- `e2e/persistence.spec.ts`: three-smazzata persistence, default Normale, persisted Facile, normal reload/resume paths;
- `e2e/guidance.spec.ts`: first-match guidance and manual dismissal surviving resume;
- `e2e/pwa.spec.ts`: warmed offline reload/resume, app-shell-only caching, cache removal preserving the save;
- `e2e/deployment.spec.ts`: build metadata/path/PWA artifact checks;
- `scripts/deployed-smoke.mjs`: real Pages manifest/icon/worker registration plus onboarding/start smoke.

The M37 implementation report explicitly leaves the second-build service-worker update path and broader browser failure coverage to M38.

The package version is still `1.1.2`; M38 owns the v1.2.0 version/release metadata and release gate.

## In scope

- Audit the current Vitest/Playwright release matrix against the M34–M37 contracts and reuse existing coverage where it is already sufficient.
- Add only the smallest missing browser-level coverage needed for the v1.2 release contract.
- Preserve browser proof for all supported match-length presets: 2, 3, and 4 smazzate.
- Add browser-level proof that legacy active-match saves accepted by the current migration layer still restore through the public application and continue as current schema-v3 state.
- Preserve browser proof for both bot profiles, including Normale default and Facile persistence.
- Add browser-level proof of M36 manual opt-out and Settings re-entry/re-enable behaviour without moving guidance into the active-match save.
- Add deterministic browser-level service-worker update coverage that proves a newly available worker does not force-reload or take over an already-open active match, and that the next safe client lifecycle can use the updated worker while the local match save remains intact.
- Add deterministic browser-level service-worker unsupported/registration-failure coverage showing that the online app still starts and an existing valid local match remains untouched/resumable.
- Fix only concrete release-blocking defects exposed by this audit, with the narrowest safe change and regression coverage.
- Bump application version metadata to `1.2.0`.
- Update release documentation for the M37 → M38 → exact-SHA v1.2.0 release path.
- Create/update `docs/milestones/reports/M38-implementation.md`.
- After independent review, use the existing exact-SHA PR CI → merge → main verify/deploy/deployed-smoke gate before tag `v1.2.0` is created.

## Out of scope

- New Burraco rules, scoring, wildcard, pozzetto, closure or turn-flow behaviour.
- New match-length presets or custom match length.
- New bot difficulty levels, stronger strategy, randomness, lookahead or bot redesign.
- New onboarding, coaching content, tutorial steps or guidance interaction model.
- Save-schema evolution beyond fixing a concrete migration defect found by M38.
- New PWA features such as background sync, push notifications, runtime API caching, cloud sync, install banners or custom update UI.
- Accounts, backend, online multiplayer, leaderboards, telemetry or analytics.
- Visual redesign, new themes, new motion/audio work or unrelated UX polish.
- Broad refactors performed only because this is a release milestone.
- New production-only debug/test hooks, query parameters or hidden routes.
- Replacing the existing GitHub Pages deployment pipeline unless a concrete release blocker requires a minimal correction.

If a discovered defect requires a material game-rule, persistence-model, bot-semantics or architecture change, report it as a blocker instead of silently expanding M38.

## Required behaviour

### 1. Release matrix is audited, not duplicated

Treat the existing suite as the starting release suite.

Map each v1.2 release requirement to an existing or new test and avoid creating parallel tests that merely rename already-covered scenarios. Existing tests count when they directly prove the contract.

At minimum the final matrix must prove in real Chromium:

- 2-smazzata match reaches its configured terminal result;
- 3-smazzata setup survives reload/resume with the same configured total;
- 4-smazzata default path remains playable through the existing bounded lifecycle coverage;
- Normale remains the default bot difficulty;
- Facile can be selected and survives reload/resume;
- first-match guidance can be dismissed and remains presentation-only;
- guidance can be explicitly re-enabled from Settings and becomes visible again in an active match without mutating the active-match save;
- warmed PWA reloads offline and resumes the saved match;
- app-shell cache removal does not remove the match save;
- worker registration/update failure cannot block normal online startup or damage the save;
- a worker update waits rather than force-reloading/taking over an active client.

### 2. Legacy save compatibility is browser-proven

Add a focused browser test for the legacy save formats that the current application intentionally accepts.

At minimum:

- a valid released v1.1.x/schema-v1 active-match save must be loadable by the current app;
- if schema-v2 compatibility remains part of the current migration code, cover it too because pre-release v1.2 development builds were deployed through `main`;
- restoration must enter the normal resume path, preserve the historical/default semantics defined by M34/M35, and continue as valid current state;
- after one ordinary committed action, persistence must remain writable in the current schema;
- malformed/unsupported legacy data must continue to fail safely through the existing validation boundary.

Prefer reusing repository fixture/build helpers. Do not add a shipped migration/debug UI.

### 3. Bot difficulty stays behavioural configuration, not a second rules engine

M38 must not alter bot legality or the Normale strategy baseline.

Browser coverage only needs to prove the product configuration path:

- fresh onboarding defaults to Normale;
- Facile can be selected;
- the chosen difficulty remains the same after reload/resume;
- hidden-information protections remain covered by the existing suite.

Do not duplicate the detailed deterministic strategy unit tests at E2E level.

### 4. Guidance opt-out and re-entry are browser-proven

Extend the existing guidance browser coverage rather than creating a parallel tutorial suite.

Prove this user flow:

1. start a guided match with the default preference;
2. dismiss the contextual guide;
3. confirm compact guidance remains and the active-match save is unchanged by that preference action;
4. open Settings and re-enable **Guida contestuale**;
5. return to the same active match and confirm contextual guidance is visible again;
6. reload/resume and confirm the preference remains independent from the active-match envelope.

Do not add guidance fields to `MatchSetup`, `GameState`, `MatchState` or the schema-v3 save envelope.

### 5. Service-worker update lifecycle is browser-proven

Add a deterministic Playwright regression for the update path left to M38 by M37.

The test must use production-style service-worker registration and must prove the lifecycle semantics, not merely inspect source text:

- establish a controlled client with an active locally saved match;
- make a distinct newer worker/build available at the same application scope;
- trigger/observe the update;
- prove the existing page is not force-reloaded and remains under the old controller while actively open;
- prove no match-save mutation/clear occurs because of the update;
- after the old client is closed or otherwise reaches the normal safe activation boundary, prove a new client can become controlled by the newer worker and the same local match remains resumable.

A test-only fixture/server/artifact transformation is acceptable when it stays outside shipped product behaviour and does not introduce a production debug hook.

Do not weaken M37 by enabling unconditional `skipWaiting`, `clientsClaim` or automatic page reload.

### 6. Service-worker failure remains a progressive enhancement

Add/retain a real-browser path where service-worker support/registration is unavailable or fails.

The online app must still:

- render normally;
- resume a valid local match when one exists;
- allow normal gameplay;
- leave the active-match save untouched by the failed PWA setup;
- emit no uncaught application error caused by the registration failure.

Use browser/test control rather than a production-visible failure switch.

### 7. Release-blocking fixes stay minimal

If the audit exposes a failing critical path:

- confirm whether the defect is product behaviour, a stale test, or test infrastructure;
- preserve established M34–M37 behaviour when the test is stale;
- change production code only for a genuine release-contract defect;
- add the narrowest regression test;
- record the deviation and reason in the M38 report.

Do not use M38 as an opportunity for cleanup unrelated to a release blocker.

### 8. Version becomes 1.2.0

Set the application release version to `1.2.0`.

At minimum:

- root `package.json` reports `1.2.0`;
- root package metadata in `package-lock.json` reports `1.2.0`;
- dependency versions are not changed merely for the application version bump;
- `README.md` identifies `v1.2.0` as the current release candidate/release version when the branch is ready for release.

The Git tag is `v1.2.0` and is created only after the post-merge production gate is green.

### 9. Release documentation is unambiguous for v1.2

Update `docs/RELEASE.md` so it clearly records:

- v1.2 / M38 / `1.2.0` / `v1.2.0`;
- M37 as the previous product milestone;
- the exact reviewed M38 HEAD as the SHA that must pass PR CI and be merged to `main`;
- the post-merge `main` workflow must verify, deploy and smoke that same SHA;
- only after those jobs are green is `v1.2.0` created on that SHA;
- previous tags remain immutable.

Keep the procedure general where possible rather than duplicating the entire release checklist.

### 10. Canonical verification and deployment invariants remain unchanged

`npm run verify` remains the single canonical implementation/PR gate and must continue to include:

1. Vitest;
2. production build;
3. Playwright Chromium E2E;
4. `git diff --check`.

The existing CI invariant remains:

- pull requests to `main` verify and do not deploy;
- a push to `main` deploys only after verify succeeds;
- Pages receives the exact `dist` artifact created by that successful verify job;
- deployed smoke runs against the resulting real Pages URL;
- deployment/smoke failure blocks release closure.

Do not add retries that hide flakes or remove critical-path tests to make the release green.

### 11. Deployed smoke stays small but real

Keep the deployed smoke focused on production reachability and high-value integration:

- deployed document reachable;
- manifest/icon URLs resolve;
- service worker registers with the correct Pages project scope;
- onboarding renders;
- a real match starts through the public UI;
- no uncaught page error on the smoke path.

Do not move the exhaustive local release matrix into deployed smoke unless a concrete production-only defect requires one additional narrow assertion.

### 12. Implementation report

Create/update `docs/milestones/reports/M38-implementation.md`.

Record concisely:

- branch and final implementation HEAD;
- files/areas changed;
- final release-matrix mapping to existing/new browser tests;
- legacy save formats browser-tested;
- service-worker update/failure test approach;
- final Vitest count;
- final Playwright Chromium count;
- build result;
- `git diff --check` result;
- final `npm run verify` result;
- whether CI/deployment files changed and why;
- deviations;
- risks/ambiguities;
- incidental changes.

Do not claim the production deployment or `v1.2.0` tag as complete from the implementation branch.

  - legacy save compatibility;

`npm run verify`

and confirm:

`git diff --check`

- leave the working tree clean;

## Completion conditions

M38 implementation is ready for review only when:

- all acceptance criteria that belong to the branch are satisfied;
- the browser release matrix is complete and non-redundant;
- the release version/docs are `1.2.0`;
- canonical verification passes;
- no unresolved blocker or important release risk is hidden;
- the implementation report is complete;
- no merge to `main` or `v1.2.0` tag has been performed by the implementer.

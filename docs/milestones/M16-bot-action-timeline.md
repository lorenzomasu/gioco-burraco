# Milestone 16 — Bot action timeline

## Goal

Make automated turns understandable to the human player without slowing or changing bot gameplay. The three bot-controlled seats currently resolve immediately and the UI jumps from the human discard to the resulting table state; M16 must expose a deterministic, chronological trace of the public actions that actually committed during those automated turns.

The trace must be produced by the bot orchestration layer from successful engine transitions, not reconstructed in React by diffing game states. It must never reveal hidden bot-hand cards, stock identities, unrevealed pozzetto contents, rejected candidates, or strategy internals.

## Context

Milestones 11 and 12 introduced deterministic bot execution and strategy. After the human ends a turn, `playBotsUntilHumanTurn` may resolve three consecutive bot turns before control returns to `player-1`. This is intentionally immediate and deterministic, but the current UI only receives the final `GameState`.

Milestone 14 wrapped the single-round state in a four-smazzate match lifecycle, while M15 made existing-meld wildcard extension history-aware. None of those milestones records an execution history.

The existing boundaries remain authoritative:

- `src/game/engine` owns game-rule legality and state transitions;
- `src/game/bot` owns deterministic automated decisions and execution;
- `GameState` models the current single-smazzata game state, not UI telemetry;
- `MatchState` owns match lifecycle and settled scoring history, not per-action presentation history;
- React renders public information and invokes domain APIs, but must not infer bot actions by reverse-engineering state differences;
- bot code may use the bot's own hand when deciding, but public trace output must respect the hidden-information guarantees documented in `docs/ARCHITECTURE.md`.

M16 is a product-observability milestone. It does not change any Burraco rule or bot ranking heuristic.

## In scope

- A typed public bot-action event model under `src/game/bot` or an equivalently appropriate bot module.
- A traced bot execution API that returns both the resulting `GameState` and the chronological public events generated by committed bot actions.
- Preservation of the existing state-only bot APIs for current callers and regression compatibility.
- Public events for:
  - draw from the stock;
  - collection of the discard pile;
  - creation of a new meld;
  - extension of an existing team meld;
  - discard;
  - pozzetto acquisition when caused by a bot action.
- Physical-card identity in events only for cards that have become public through a committed meld, extension, or discard.
- A round-local React timeline showing bot actions in chronological order.
- Correct behaviour when consecutive bot turns are resolved in one automatic chain.
- Correct behaviour when a bot action completes the round.
- Reset of the bot-action timeline when a new smazzata or new match starts.
- Deterministic regression tests for event order, hidden-information safety, state equivalence, match/UI integration, and existing bot behaviour.
- A focused architecture documentation update for the new public-event boundary.

## Out of scope

- Changing bot strategy, ranking weights, candidate limits, draw-source heuristics, tie-breaking, difficulty, personalities, lookahead, probability modelling, or learning.
- Adding delays, animations, timers, step-by-step bot playback, replay controls, undo, or pausing between automated actions.
- Recording human-player actions in the same timeline.
- Persisting the action timeline in `GameState`, `MatchState`, local storage, a backend, or save/resume data.
- Cross-round action history: each new smazzata starts with an empty timeline.
- Network/multiplayer synchronization or spectator mode.
- Exposing rejected/considered bot candidates, heuristic scores, hidden bot-hand cards, stock card identities, stock order, or unrevealed pozzetto cards.
- Major visual redesign or unrelated M10 UI polish.
- New Burraco rules or changes to `docs/RULES.md`.

## Required behaviour

### 1. Bot execution exposes one public event contract

Introduce one exported discriminated-union event type for committed bot actions.

The exact type and field names are implementation choices, but the model must be able to represent at least:

- a bot drawing from the stock;
- a bot collecting the discard pile, including the public count of cards collected;
- a bot creating a new meld, including the physical cards that became public;
- a bot extending an existing team meld, including the physical cards newly added and enough stable target information to describe the committed action;
- a bot discarding one physical card;
- a bot taking the pozzetto, distinguishing acquisition *al volo* from acquisition *con lo scarto* when that distinction is known from the committed transition.

Every event must identify the acting `PlayerId`.

Events are execution facts, not strategy explanations. Do not include candidate scores, tie-break strings, future-meld counts, opponent-help flags, internal validation reasons, or other ranking metadata.

### 2. Hidden information remains hidden

The public trace must obey the same visibility guarantees as the UI.

A stock-draw event must not contain the drawn card's ID, rank, suit, deck number, label, or any other value from which that hidden card can be identified.

A pozzetto-acquisition event must not contain the identities or faces of the newly acquired pozzetto cards.

A discard-pile collection event must not expose private information created by the bot decision process. The timeline only needs the collection fact and public count; it does not need to copy the full pile into the event.

Cards may be attached to a trace event only when the committed action itself makes those physical cards public:

- cards played into a new meld;
- cards added to an existing meld;
- the discarded card.

If a card drawn from the stock is immediately melded or discarded later in the same turn, it may then appear in that later public action event.

### 3. Events come from committed execution, never candidate simulation

Bot strategy currently evaluates multiple candidate states before selecting a move. M16 must not emit events while:

- checking whether the discard pile is useful;
- generating meld candidates;
- generating extension candidates;
- ranking candidate actions;
- generating or ranking discard candidates;
- probing engine commands for legality.

An event is emitted only after the bot orchestration layer selects an action and commits the corresponding already-valid engine result as the next current state.

This requirement is critical: the event stream must describe what actually happened, exactly once.

### 4. Add traced execution without breaking the state-only API

Keep the existing public behaviour of:

- `playBotTurn(...): GameState`;
- `playBotsUntilHumanTurn(...): GameState`.

Add traced equivalents or one shared internal execution primitive from which both state-only and traced APIs derive.

There must be one bot-turn execution path. Do not copy the automation loop into a second implementation just to collect events.

For the same input state, player, and limits:

- the traced API's resulting state must equal the state returned by the existing state-only API;
- safety limits and `BotAutomationError` behaviour must remain equivalent;
- bot decisions must remain deterministic.

### 5. Event order mirrors committed action order

Within one bot turn, events must appear in the same order as the committed transitions.

Examples:

- stock draw → meld → extend → discard;
- discard-pile collection → meld → discard;
- meld that empties the first hand → pozzetto acquisition event immediately after that meld event;
- discard that empties the first hand → discard event followed by pozzetto acquisition *con lo scarto*;
- discard that closes the round → discard event is still present before the round is reported completed.

No duplicate event may be produced for one committed command.

When `playBotsUntilHumanTurn` resolves multiple bots, its returned event list must be the stable concatenation of each turn's events in actual execution order.

### 6. Pozzetto acquisition is represented as a public side effect

When a committed bot meld, extension, or discard transitions that bot's team from `hasTakenPozzetto: false` to `true`, append a separate public pozzetto event.

The event must:

- identify the acting player;
- distinguish `flight` / *al volo* for acquisition caused by playing cards without ending the turn;
- distinguish `discard` / *con lo scarto* for acquisition caused by the final discard of the first hand;
- reveal no pozzetto card identities.

Do not create pozzetto events merely because candidate generation simulated such a state.

### 7. Meld and extension events preserve public physical-card identity

For committed new-meld and extension actions, event cards must correspond exactly to the physical card IDs removed from that bot's hand by the selected action.

Equivalent cards from the two decks are not interchangeable.

For a new meld, the event may also carry the resulting meld index or equivalent stable location information.

For an extension, the event must carry enough target information for the UI to say which team meld was extended without re-deriving the action by comparing the entire table state.

Do not include unrelated pre-existing meld cards in the event's "played cards" collection.

### 8. React owns only timeline presentation and round-local retention

`GameTable` may keep the bot event history as transient React state.

Do not add this timeline to `GameState` or `MatchState`.

During one smazzata:

- append every event returned by each automatic bot chain;
- preserve chronological order;
- keep prior bot events visible after control returns to the human;
- if a bot closes the round or triggers draw-pile exhaustion, the completed-round UI must still be able to show the bot timeline from that smazzata.

Starting the next smazzata must clear the previous round's timeline before recording any immediately automated events in the fresh round.

Starting a completely new match must also clear the prior timeline.

### 9. Timeline UI is public, readable, and non-authoritative

Add a compact UI section such as "Azioni dei bot" / "Cronologia bot".

The exact visual treatment is an implementation choice, but it must:

- render events in chronological order;
- show the existing player display name for each event;
- distinguish stock draw, discard-pile collection, new meld, extension, discard, and pozzetto acquisition;
- render existing public card labels for melded/extended/discarded cards using the current presentation helpers rather than inventing a parallel rank/suit naming system;
- expose semantic list/region structure suitable for Testing Library and screen readers;
- contain no controls that change game state.

The timeline must not determine whether an action was legal, whether a pozzetto was taken, or what a wildcard represents. It only renders the event facts returned by the bot layer.

### 10. Initial/pending bot automation uses the same traced path

The current UI may automatically resolve bots while preparing:

- an injected initial state;
- a newly created match;
- a newly advanced round.

Those paths must use the same traced automation boundary as post-discard bot resolution when bots are pending.

Do not create a special UI-only way of reconstructing events for initial automation.

### 11. Existing game and match behaviour is unchanged

M16 must not alter:

- engine legality;
- wildcard-replacement semantics from M15;
- round completion;
- scoring;
- four-round settlement and VP calculation;
- bot strategy choices;
- human controls;
- match reset and next-round transitions;
- deterministic seeded game behaviour.

The only domain-level addition is public execution telemetry around bot actions.

## Acceptance criteria

- [ ] AC1 — A typed discriminated-union bot public-event model exists and every event identifies the acting player.
- [ ] AC2 — A traced single-bot-turn API returns the same resulting `GameState` as the existing state-only `playBotTurn` for the same input and limits.
- [ ] AC3 — A traced consecutive-bot API returns the same resulting `GameState` as `playBotsUntilHumanTurn` and concatenates events in deterministic execution order.
- [ ] AC4 — Stock-draw events reveal no physical card identity or face information.
- [ ] AC5 — Pozzetto-acquisition events reveal no pozzetto card identities.
- [ ] AC6 — Candidate generation, candidate ranking, legality probes, and draw-source simulations emit no public events.
- [ ] AC7 — New-meld events contain exactly the physical cards committed from the bot hand and preserve their IDs.
- [ ] AC8 — Extension events contain exactly the newly added physical cards and stable target information; they do not copy all pre-existing meld cards as newly played cards.
- [ ] AC9 — Discard events contain the exact physical discarded card.
- [ ] AC10 — Pozzetto acquisition caused by meld/extension is emitted as *al volo* after the triggering action; acquisition caused by discard is emitted as *con lo scarto* after the discard event.
- [ ] AC11 — A bot turn that performs multiple actions produces one event per committed action in exact chronological order with no duplicates.
- [ ] AC12 — Multiple consecutive bot turns preserve player order and event order in one combined trace.
- [ ] AC13 — Existing bot safety-limit errors and deterministic strategy choices are unchanged.
- [ ] AC14 — `GameState` and `MatchState` do not gain action-history fields.
- [ ] AC15 — The UI displays a chronological round-local bot timeline using player names and existing card-presentation helpers.
- [ ] AC16 — Hidden stock cards and hidden pozzetto contents do not appear in rendered timeline text, accessible names, DOM attributes, or test-visible output unless a later committed public action reveals that specific card.
- [ ] AC17 — The timeline remains available on the completed-round view when the round contains bot events.
- [ ] AC18 — Starting the next smazzata clears the previous round's timeline; starting a new match also clears it.
- [ ] AC19 — Initial/pending bot automation, post-human-discard automation, next-round preparation, and new-match preparation use the same traced automation mechanism.
- [ ] AC20 — Existing engine, scoring, match, wildcard, bot, and UI tests remain green and `npm run verify` passes.

## Required tests

Add deterministic automated tests covering at least the following.

### Bot trace domain tests

- traced stock draw emits a draw event without any card identity;
- traced discard-pile collection emits one collection event with the correct public card count;
- a simple bot turn emits acquisition then discard in that order;
- a turn with a new meld emits acquisition → meld → discard in order;
- a turn with an extension emits the extension event with the exact added physical card ID;
- a bot that performs multiple meld/extension actions emits each committed action exactly once;
- a meld or extension that takes the pozzetto emits the triggering action followed by `take-pozzetto: flight`;
- a discard that takes the pozzetto emits discard followed by `take-pozzetto: discard`;
- a bot discard that closes the round still appears in the trace;
- a bot discard that ends the round through draw-pile exhaustion still appears in the trace;
- a three-bot chain produces events grouped chronologically by the actual player sequence;
- traced and untraced APIs return deeply equivalent resulting game state;
- action limits / bot-turn limits throw the same `BotAutomationError` conditions in traced and state-only entry points.

### Hidden-information mutation-resistant tests

Include tests that would fail if:

- the stock-draw event accidentally included the drawn card object, ID, label, rank, suit, or deck number;
- pozzetto card identities were attached to the pozzetto event;
- candidate generation emitted an event for an action that was considered but not selected;
- the discard-pile utility simulation emitted duplicate collection or meld events;
- a newly melded physical copy were replaced by an equivalent card from the other deck in the event;
- an extension event were reconstructed from final meld contents and therefore misidentified old table cards as newly played.

### UI integration tests

- after the human discards and three bots auto-play, the timeline shows their events in chronological order and control returns to the human;
- a visible bot meld/extension/discard card uses the existing card label formatting;
- a stock draw does not render the drawn hidden card label;
- a pozzetto event does not render any newly acquired hidden card labels;
- the timeline remains present when a bot closes the round;
- beginning smazzata 2 clears smazzata 1 bot events;
- "Nuova partita" clears the previous match's bot events;
- an injected/pending bot turn on initial/new-round preparation produces timeline events through the same traced path;
- existing human controls and match result UI remain unchanged.

## Documentation updates

Do not add a new Burraco rule to `docs/RULES.md`: M16 changes observability, not gameplay legality.

Update `docs/ARCHITECTURE.md` with a focused bot-observability invariant:

- bot public action events are transient execution metadata produced by the bot orchestration layer;
- they are not stored in `GameState` or `MatchState`;
- React renders those events but does not infer them from state diffs;
- public events must never expose stock identities, unrevealed pozzetto contents, rejected candidates, or other hidden strategy information.

Do not document animations, replay, persistence, or future multiplayer behaviour as implemented.

## Verification

Before completion, run:

`npm run verify`

All existing and new tests must pass.

## Completion conditions

The milestone is complete only when:

- all acceptance criteria are satisfied;
- traced and state-only bot execution are behaviourally equivalent;
- hidden-information tests prove the public trace does not leak private cards or strategy internals;
- the round-local UI timeline works for normal bot chains and bot-caused round completion;
- required tests exist and pass;
- `npm run verify` passes;
- documentation is consistent with the new architecture boundary;
- no unrelated bot-strategy, engine-rule, match, or visual-refactor scope was introduced.

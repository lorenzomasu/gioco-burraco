# Milestone 33 — V1.1 Hardening & Release

## Goal

Turn the integrated M27–M32 v1.1 product into a verified production release without adding new creative or gameplay scope.

M33 closes remaining browser-level release gaps, preserves the already-covered critical paths introduced across M27–M32, updates release metadata to `1.1.0`, and uses the existing review → PR CI → merge → main verify/deploy/deployed-smoke release gate before tag `v1.1.0` is created.

This is a hardening and release milestone. It must prefer small test/release changes over redesign or feature work.

## Context

The starting baseline is current `main` after M30–M32 are integrated.

The v1.1 cycle already provides:

- M27 tabletop-first application composition;
- M28 complete face-up discard-pile presentation, including long-pile scrolling and empty-pile handling;
- M29 hand reorder, optional sorting, pointer/touch direct manipulation and keyboard/button fallbacks;
- M30 presentation-only card motion and bot choreography, with reduced-motion support and cancellation on session replacement/unmount;
- M31 short synthesized sound effects with browser activation, mute/volume controls and separately persisted audio preferences;
- M32 shared Settings/Help, accessible in-app new-match confirmation, resume feedback, live cumulative score and polished between-round/final views;
- the unchanged deterministic Burraco engine, bot legality, hidden-information boundary and M22 active-match save schema;
- Playwright Chromium as part of the canonical `npm run verify` gate;
- GitHub Pages deployment from the exact verified `dist` artifact plus a deployed Chromium smoke.

The current browser suite already covers most of the M33 roadmap matrix:

- `e2e/discard-pile.spec.ts`: long piles, local scrolling, empty-pile result, keyboard collection, resumed long pile and narrow/desktop layout;
- `e2e/hand-manipulation.spec.ts`: pointer, touch, keyboard-only fallbacks and 320 px overflow protection;
- `e2e/persistence.spec.ts`: save/reload/resume and pending bot playback restoration;
- `e2e/mobile.spec.ts`: 320 px primary interaction smoke;
- `e2e/lifecycle.spec.ts`: bounded complete four-smazzata match;
- `e2e/app-shell.spec.ts`: 320/390 px shell, Settings/Help focus, keyboard abandonment flow, resume status, muted-audio + reduced-motion integrated play;
- `e2e/motion.spec.ts`: real source-to-destination flights and reduced-motion suppression;
- `e2e/hidden-information.spec.ts`: opponent-hand secrecy;
- `e2e/deployment.spec.ts` and `scripts/deployed-smoke.mjs`: project-path/deployment smoke infrastructure.

The primary browser-level gap visible at preparation time is explicit proof that an in-flight M30 animation can be interrupted by session replacement/unmount without leaving a stale proxy, stale callback or application error.

## In scope

- Audit the current Playwright release matrix against the M33 roadmap outcome.
- Reuse existing E2E coverage when it already proves an M33 requirement; do not duplicate equivalent scenarios merely to create an M33-specific file.
- Add focused browser-level coverage for interruption/cancellation of an active M30 animation during session replacement/unmount.
- Fix only concrete release-blocking defects exposed by the M33 audit/tests, using the smallest change that preserves existing architecture.
- Keep the existing browser critical paths green for:
  - full discard display;
  - long and empty discard piles;
  - save/reload/resume;
  - audio disabled;
  - reduced motion;
  - keyboard-only operation;
  - touch/direct manipulation;
  - approximately 320–390 px mobile layouts;
  - hidden-information protection;
  - complete four-smazzata match lifecycle.
- Update package/repository release version from `1.0.0` to `1.1.0`.
- Update product/release documentation where it still identifies v1.0.0 as the current release or uses v1-only release examples that would make the v1.1 procedure ambiguous.
- Preserve the existing canonical verification and Pages deployment pipeline unless a concrete M33 release defect requires a minimal correction.
- Create/update `docs/milestones/reports/M33-implementation.md`.
- After independent review and merge, complete the existing exact-SHA production release gate and create tag `v1.1.0` only after that gate is green.

## Out of scope

- New Burraco rules, rule corrections not already identified by a release-blocking regression, scoring changes or match-structure changes.
- Bot-strategy improvements, difficulty levels or new bot behaviour.
- Save-schema changes, migrations or new persistence scope.
- New interaction models, controls, settings, onboarding steps or help topics.
- New animations, sound effects, visual redesign, branding work or creative polish.
- Background music.
- Multiplayer, accounts, cloud sync, leaderboards, telemetry or analytics.
- PWA/service-worker/offline-install work.
- Router or hosting redesign.
- Broad refactors undertaken only because M33 is the final milestone.
- New test-only production APIs, query parameters, debug routes or hidden controls.
- Screenshot/pixel-diff visual regression infrastructure.
- Expanding the release gate to Firefox/WebKit/device-farm coverage without a concrete discovered blocker.
- Moving or rewriting the existing `v1.0.0` tag.

If M33 exposes a defect whose safe correction requires changing game rules, bot legality, hidden-information semantics, persistence format or another high-risk architectural boundary, do not silently absorb it into this release milestone. Report it as a blocking finding so it can be isolated as a corrective milestone.

## Required behaviour

### 1. Preserve and audit the browser release matrix

Treat the current Playwright suite as the starting release suite, not as disposable scaffolding.

The implementation must map the M33 roadmap matrix to existing tests and confirm that the release gate still proves, through real browser behaviour:

- the complete face-up discard pile is rendered in chronological order;
- a long discard pile remains inspectable through local scrolling without document-level horizontal overflow;
- collecting the pile reaches the correct empty-pile presentation;
- save → reload → resume preserves committed progress and safely recreates transient bot playback;
- muted audio never blocks gameplay and the mute preference remains a presentation preference outside the active-match save;
- `prefers-reduced-motion: reduce` leaves the game fully playable and suppresses decorative card flights;
- keyboard-only fallbacks remain available for the core interaction paths;
- touch interaction/direct manipulation remains usable at the supported mobile widths;
- the app remains usable around 320 px and 390 px without document-level horizontal overflow;
- hidden opponent cards/identities remain absent from player-visible DOM content;
- one bounded deterministic browser path reaches the final result after all four smazzate.

Existing tests count toward these requirements when they already assert the behaviour. Add or reshape tests only when the current assertion is missing, stale or too indirect to protect the release contract.

Do not create a second parallel E2E matrix that tests the same behaviour with renamed scenarios.

### 2. Interrupted animation must be browser-proven

Add a focused Playwright regression proving the M30 interruption contract in a real browser.

The scenario must create an actual card-flight condition and replace/unmount the active game session before that presentation work can be allowed to persist.

After the replacement:

- no `.motion-proxy` from the previous session remains attached;
- no stale animation completion/callback mutates the replacement view;
- the replacement/onboarding/new session remains stable;
- no uncaught page error is emitted;
- committed domain state remains the source of truth and no artificial rollback is introduced.

The test may instrument the browser Web Animations API from the test side when needed to make interruption deterministic, but it must not add a production test hook or change gameplay timing merely to make the test pass.

Prefer extending `e2e/motion.spec.ts` and reusing existing real user flows rather than creating new production-facing mechanisms.

### 3. Audio-off and reduced-motion are release fallbacks, not alternate game modes

The release suite must keep at least one integrated browser path where:

- sound is muted through the real Settings UI;
- reduced motion is enabled through browser media emulation;
- the user can still perform a normal gameplay action;
- no decorative animation or audio preference becomes required for state comprehension or command completion.

The existing M32 browser test may satisfy this if it remains sufficiently explicit.

Do not add game-state fields, save fields or engine branches for these preferences.

### 4. Keyboard, touch and mobile remain first-class fallbacks

Keep browser-level proof that:

- keyboard-only users can perform the non-drag fallback actions required by M29/M32;
- touch users can reorder/directly manipulate cards without breaking ordinary page scrolling;
- the shell, table, settings/help and primary actions remain within the supported 320–390 px mobile envelope;
- intentionally scrollable local card surfaces may scroll horizontally, but the document itself must not.

Do not replace functional assertions with screenshot-only checks.

### 5. Release-blocking fixes must stay minimal

If the M33 audit uncovers a failing existing critical path:

- first confirm whether the defect is in test assumptions or product behaviour;
- preserve established M27–M32 behaviour when the test is stale;
- fix product code only when the user-visible release contract is genuinely broken;
- keep the correction local and add regression coverage;
- do not refactor unrelated code while fixing it.

Any material deviation, newly discovered risk or corrective product change must be recorded in the M33 implementation report.

### 6. Version becomes 1.1.0

Set the release version to `1.1.0`.

At minimum:

- root `package.json` reports `1.1.0`;
- root package metadata in `package-lock.json` reports `1.1.0`;
- `README.md` identifies `v1.1.0` as the current release when the branch is ready for release;
- no dependency versions are changed merely to perform the application version bump.

The Git tag is `v1.1.0`, created only at the post-merge release gate.

### 7. Release documentation must be unambiguous for v1.1

Update `docs/RELEASE.md` only as needed so the documented procedure clearly applies to this release.

It must make clear that for v1.1:

- M32 is the previous product milestone;
- M33 is the independently reviewed release milestone;
- the reviewed M33 HEAD must be the same SHA verified by PR CI and merged to `main`;
- the post-merge `main` workflow must verify, deploy and smoke that exact SHA;
- tag `v1.1.0` is created only after those jobs are green;
- the package version must match the tag without the `v` prefix;
- existing release tags, including `v1.0.0`, remain immutable.

Prefer generalising the release checklist enough to support later versions rather than duplicating a second full procedure, provided the concrete `v1.1.0` action remains clear.

Update `README.md` for the current release version. Do not introduce a changelog system unless a concrete existing repository requirement makes it necessary.

### 8. Canonical verification remains the gate

`npm run verify` remains the single canonical branch/PR verification command.

It must continue to cover:

1. Vitest;
2. production build;
3. Playwright Chromium E2E against the built application;
4. `git diff --check`.

Do not weaken the gate, add retries to hide flakes or remove existing critical-path tests to make M33 green.

The implementation may reorganize an E2E helper only when that is necessary to keep the release suite deterministic and maintainable.

### 9. CI/deployment remains exact-SHA

The existing GitHub Actions invariant must remain:

- pull requests to `main` verify but do not deploy;
- a push to `main` deploys only after the canonical verify job succeeds;
- Pages receives the `dist` produced by that successful verify job;
- the deployed smoke runs against the resulting real Pages URL;
- deployment/smoke failure blocks release closure.

Do not introduce a second release pipeline if the existing `.github/workflows/ci.yml` already satisfies the requirement.

A CI/deployment file change is warranted only for a concrete defect discovered while implementing M33.

### 10. Deployed smoke remains small but real

The post-merge deployed smoke must continue to prove that the deployed v1.1 artifact:

- is reachable at the real Pages project URL;
- has no uncaught page error on the smoke path;
- renders onboarding;
- starts one real match through the public UI;
- reaches the table and `Smazzata 1/4`.

Do not turn the deployed smoke into a duplicate of the full local Playwright suite.

If the existing smoke already satisfies this contract, keep it unchanged.

### 11. No hidden-information or domain-boundary regression

M33 must not move motion, drag, audio, settings/help, dialog or E2E concerns into game-domain state.

It must preserve:

- engine authority for legal moves;
- deterministic bot legality/strategy behaviour;
- hidden opponent-hand information;
- the M22 save schema and validation boundary;
- presentation-only motion/audio/transient UI state;
- current scoring and match lifecycle semantics.

`docs/RULES.md` should remain unchanged unless an actual documentation defect is discovered. Any such incidental correction must be explicitly reported and must not redefine the v1.1 rules baseline.

### 12. Implementation report

Create `docs/milestones/reports/M33-implementation.md` from the normal report template.

Record at least:

- branch and final implementation HEAD;
- files/areas changed;
- how the M33 browser matrix maps to existing/new tests;
- the explicit interrupted-animation coverage added;
- final Vitest count;
- final Playwright Chromium count;
- build result;
- `git diff --check` result;
- final `npm run verify` result;
- deviations;
- risks/ambiguities;
- incidental changes;
- whether CI/deployment files changed and why.

Do not claim the production deployment or `v1.1.0` tag as complete from the implementation branch.

## Verification

M33 is a standalone release milestone.

Before the implementation branch is ready for review:

1. inspect the complete M33 diff;
2. run the canonical repository gate:

`npm run verify`

3. fix M33-caused failures and rerun the necessary checks;
4. complete `docs/milestones/reports/M33-implementation.md`;
5. commit and push only `milestone-33-v1.1-hardening-release`;
6. stop before merge/tag.

## Completion conditions

### Implementation completion

The implementation agent may declare the branch ready for independent review only when:

- all branch-implementable acceptance criteria are satisfied;
- the browser matrix has been audited without redundant duplication;
- the interrupted-animation gap has explicit browser regression coverage;
- version/documentation changes for `1.1.0` are complete;
- `npm run verify` passes;
- the implementation report is complete;
- the branch is committed and pushed;
- no merge or release tag has been performed.

### Milestone/release completion

M33 and v1.1 are closed only after the independent release gate confirms, for one exact commit SHA:

1. M33 review has no unresolved blocker or important finding;
2. the reviewed branch HEAD is unchanged;
3. PR CI is green on exactly that HEAD;
4. exactly that HEAD is merged into `main`;
5. the `main` workflow verifies that exact SHA;
6. the verified `dist` artifact from that workflow is deployed successfully to GitHub Pages;
7. the deployed Chromium smoke is green against the real Pages URL;
8. the deployed site is reachable as the expected v1.1 Burraco application;
9. tag `v1.1.0` is created on that exact SHA;
10. the remote tag is verified to resolve to that exact release SHA.

A merge alone does not close M33. A green PR alone does not close v1.1.
